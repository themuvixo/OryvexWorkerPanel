How a release happens

  1. You push to mainThe Release workflow builds and tests every push.
  2. It picks a versionIf package.json holds a version that isn't tagged yet, that version ships. Otherwise the patch number is bumped and committed for you.
  3. It tags and publishesTag vX.Y.Z, a GitHub Release with notes from CHANGELOG.md, plus worker-single-file.js, the Pages zip and SHA256SUMS.txt.
  4. Panels see itEvery panel built from the repo lights a NEW badge on Update within six hours.

Docs-only pushes (site/, *.md) never cut a release.

Control the version

  • Minor or majorActions → Release → Run workflow, pick minor / major, or type an exact version.
  • By handnpm run release:minor, edit CHANGELOG.md, push. That exact version ships.
  • Manual tagPush vX.Y.Z matching package.json and it's released as-is.
  • Turn off auto-bumpRepository variable AUTO_BUMP = none (or minor).
  • Protected mainAdd a fine-grained token with Contents: write as secret RELEASE_TOKEN.

Update from the panel

  1. Save a Cloudflare tokenTop bar → CF daily → token with Workers Scripts: Edit.
  2. Open UpdateIt shows installed → latest, release date and notes.
  3. Install updateThe bundle is downloaded from the release, its version checked, and deployed with your KV bindings, variables and secrets kept.

How the check works

  • Releases onlyOnly published Releases count, so "update available" always has a file behind it.
  • Rate-limit proofUses the GitHub API first; if it's throttled, falls back to the releases/latest redirect on github.com.
  • CachedResults are kept 10 minutes on the Worker. Check now always asks GitHub again.
  • VerifiedThe downloaded bundle must carry the release's version on line 1, or nothing is deployed.

Bind an optional GITHUB_TOKEN secret (no scopes needed for public repos) to lift the API limit from 60 to 5,000 checks an hour.
